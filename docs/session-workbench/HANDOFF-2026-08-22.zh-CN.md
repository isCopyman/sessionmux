## 1. 心智模型（两条，理解 profile 子系统的钥匙）

### 1.1 双模规则

用户亲自拍板的设计决策：

> **codeg 要么什么都不设（跟随 CLI），要么用 `--settings` 覆盖层统管。没有第三种状态。**

对应代码（`src-tauri/src/commands/claude_profile.rs`）：

- `follow-default` → 提前返回，**一个字节都不写**
- 任何选中的 profile → 先清扫 profile 拥有的 env 键，再把三个 `ANTHROPIC_*` 置空
  （空值 = 让 spawn 层 `env_remove`，挡住宿主 shell 继承的凭据），然后按 kind
  挂 `--settings` 覆盖层

**已实测的事实**（别再重新推导）：

- 项目级 `.claude/settings.json` 优先级高于进程环境变量
- flag 层（`--settings`）上的 `ANTHROPIC_BASE_URL: ""` 既赢得合并、又被读成"未设置"
- Claude Code 的优先级：`managed > --settings > local > project > user`

### 1.2 谁在说真话，谁在说谎 ★

**这条是本轮最重要的认知，之前绕了很多弯路才想明白，别再绕一遍。**

界面上关于 profile 有三个信息源，可信度完全不同：

| 界面元素 | 数据从哪来 | 可信吗 |
|---|---|---|
| **模型下拉列表** | CLI 通过 ACP 上报的 `SessionConfigOptionInfo` | **诚实**。它如实反映**正在跑的那个进程** |
| **profile chip** | 前端本地 state（`setSelectedId`） | **说谎**。它显示的是**你点了什么**，不是**在跑什么** |
| 绿色"切换成功"提示 | `affectedRunningSessions < 1` 分支 | **说谎**。"没有活会话受影响"被当成了成功 |

用户当时的原话问题是：「如果后端不知道我选了 CPA，那为啥 chip 显示 CPA 是正确的？」

答案在 `src/components/chat/claude-profile-selector.tsx:114` 的 `handleSelect`：

```tsx
if (conversationId == null) {
  setSelectedId(profileId)        // 纯前端 state，后端一个字都没收到
  onPendingProfileChange?.(profileId)
  return
}
await conversationSetClaudeProfile(conversationId, profileId)   // 有行才走这条
```

所以 chip「永远正确」，因为它只是**把你的点击回显给你看**。它跟后端一次都没通过气。

**推论（很重要）**：现象是「chip 说 CPA、模型列表说官方」时，
**不是模型列表坏了，是 chip 在撒谎**。曾经花了一整轮去查"模型下拉为什么不显示
槽位重映射"，那个诊断是错的，已作废。

**另一条推论**：模型/mode/effort 这些列表**只能靠重连刷新**——它们是 CLI 在 ACP
握手时报上来的，不是从 settings.json 推导的。所以"切 profile"在物理上就等于
"重连一次 ACP"，没有别的办法。

## 4. 未完成的活，按优先级

### 4.1 ✅ 已修：切 profile 只生效一次（`55655610`）

留在这里是因为**根因值得记住**，不是待办。

用户原话："第一次加载的时候 model 倒是会跟着变，但是后面的切换都不会。"
**注意是「次序」不是「方向」**——第 3 次切换和第 1 次方向相同，照样失败。

**根因**：`SessionState::conversation_id` 在生产代码里只由 `ConversationLinked` /
`ConversationForked` 赋值（`session_state.rs:1006/1016`），这两个事件只在**会话行被创建**
时才发。重连到已存在的行不发 → 重启出来的新连接**未绑定** →
`mark_conversation_config_stale`（扫描 `state.conversation_id`）从此再也找不到 →
`affected_running_sessions = 0` → chip 走「没有活会话」分支弹绿色成功提示 →
没横幅、没重启 → 会话继续跑旧 profile。

**实测证据**（CDP 连真实 Tauri WebView2，不是读代码推的）：
三次切换，`tauri-dev.log` 里只有第一次有 `disconnect` + `spawning`；
数据库每次都正确更新；DOM 里查不到 stale 横幅。

**当时修复**：`ConnectionManager::bind_conversation`，两条 connect 路径 spawn 成功后调用。
随后已进一步收敛为构造期身份约束：Desktop/Web 共用 `acp_connect_core`，持久会话的
`conversation_id/folder_id` 在连接发布前绑定，冲突重绑被拒绝，不再依赖 spawn 后字段补丁。
用户已确认「已有历史的会话里切换是对的」。

**影响面不止 profile**：任何按 conversation 扫描连接的查找在重连后都会失效
（例如 `acp_get_session_snapshot_by_conversation_core`）。这个修复一并解决。

教训已进 `LESSONS.zh-CN.md` **L15**。

## 7. 会咬人的坑

**1. 门的退出码会骗人。**
`cmd | tail; echo $?` 报的是 `tail` 的状态，不是工具的。用 `${PIPESTATUS[0]}`。
今晚有一批门是这么"通过"的，重跑才发现。任务书里必须明写这一条。

**2. 门命令别把失败详情 tail 掉。**
kanban1 那次 vitest 挂了 1 个，但我只留了汇总行，**失败用例名没抓到**，
只能干净重跑一遍才确认是抖动。留详情。

**3. 工人会虚构核验。** 承重结论必须主会话亲自抽验。
splithelpers 那条做了机器对拍才敢合。

**4. 明文 token。** 读 profile 时写了个掩码函数，但只递归了 dict——
而 `settingsJson` 是个**字符串**字段，里面的 `ANTHROPIC_AUTH_TOKEN` 就原样打出来了。
**读 profile 一律先按字符串脱敏。**

**5. `TaskStop` 会留下孤儿孙进程。**
误杀过自己的 `pnpm tauri dev`，`next dev` 变孤儿还占着 `.next/dev/lock`。
另外 cli-delegate 作业记录显示 `partial/124` 之后，**grok.exe 子进程可能还活着**——
今晚就捡到两个孤儿（已杀）。判"没有在跑的作业"要 `tasklist` 复核，别只看注册表。

**6. Git Bash 里 `taskkill /PID` 的路径会被改写**，前面加 `MSYS_NO_PATHCONV=1`。

**7. 别 sleep 轮询。** 用户当场批评过两次。用后台 shell。

**8. 开场那份 gitStatus 快照会过期。** 它是会话开始时的照片，不会更新。
要说"当前状态"必须重新查。

**9. 靠读代码猜根因，今晚连错三次**（已记进 LESSONS **L15**）：
- "模型下拉不显示槽位重映射" —— 被用户截图直接推翻
- "`selectorsCache` 的 agentType 键导致过期" —— 真缺陷，但不是这个症状
- "`handledStaleRef` 从不复位" —— 重连会清 `configStale`，它会复位

**先用 CDP 拿现象，再去读代码。** 反过来做，就是今晚这个下场。

**10. 写"我们没有 X"之前，先在 `docs/session-workbench/` 搜一遍。**
断言过"CDP 连不上 Tauri"，结果手册 §4.5 早就写了。这个仓库的文档比你以为的全。

**11. 分清「方向」和「次序」。**
一开始把 bug 描述成"切回去不更新"（方向），用户纠正后重测，
发现第 3 次切换方向和第 1 次相同、照样失败——是**次序**问题。
「只生效一次」这个形状，先怀疑索引/绑定丢失，别去查业务分支。

**12. 静默成功比报错难查十倍。**
`affectedRunningSessions < 1` 被当成"成功"弹绿色提示，把一个彻底失效的操作
伪装成正常。查 bug 时优先怀疑这种"什么都没发生但显示成功"的分支。
