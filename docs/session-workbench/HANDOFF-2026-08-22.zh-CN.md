## 1. 你需要的心智模型：双模规则

这是用户亲自拍板的设计决策，是理解整个 Claude profile 子系统的钥匙：

> **codeg 要么什么都不设（跟随 CLI），要么用 `--settings` 覆盖层统管。没有第三种状态。**

对应到代码（`src-tauri/src/commands/claude_profile.rs`）：

- 任何选中的 profile → `:773` 先清扫 profile 拥有的 env 键，`:779-786` 把三个
  `ANTHROPIC_*` 置空（空值 = 让 spawn 层 `env_remove`，挡住宿主 shell 继承的凭据），
  然后按 kind 挂 `--settings` 覆盖层

**已实测的事实**（别再重新推导）：

- 项目级 `.claude/settings.json` 优先级高于进程环境变量
- flag 层（`--settings`）上的 `ANTHROPIC_BASE_URL: ""` 既赢得合并、又被读成"未设置"
- Claude Code 的优先级：`managed > --settings > local > project > user`

### ✅ 已修：切 profile 只生效一次（`55655610`）

**这才是用户报的那个 bug。** 之前本节写的「模型下拉误导」诊断**是错的，已作废**——
模型列表一直是诚实的，它如实反映正在跑的进程；说谎的是 chip 和那句「切换成功」。

用户原话："第一次加载的时候 model 倒是会跟着变，但是后面的切换都不会。"
**注意是「次序」不是「方向」**——第 3 次切换和第 1 次方向相同，照样失败。

**根因**：`SessionState::conversation_id` 在生产代码里只由 `ConversationLinked` /
`ConversationForked` 赋值（`session_state.rs:1006/1016`），这两个事件在**会话行被创建**
时才发。重连到已存在的行不发 → `reapplyConfig` 重启出来的新连接**未绑定** →
`mark_conversation_config_stale`（扫描 `state.conversation_id`）从此再也找不到 →
`affected_running_sessions = 0` → chip 走「没有活会话」分支弹绿色成功提示 →
没横幅、没重启 → 会话继续跑旧 profile。

**实测证据**（CDP 连真实 Tauri WebView2，不是读代码推的）：
三次切换，`tauri-dev.log` 里只有第一次有 `disconnect` + `spawning`；
数据库每次都正确更新（`follow-default` ↔ `imported`）；DOM 里查不到 stale 横幅。

**修复**：`ConnectionManager::bind_conversation`，在两条 connect 路径
（`commands/acp.rs`、`web/handlers/acp.rs`——两边本来就手握 `conversation_id`，
只是从来没往 state 上写）spawn 成功后调用。两个测试在 `manager.rs`。
Rust 2778 通过。

**影响面不止 profile**：任何按 conversation 扫描连接的查找在重连后都会失效
（例如 `acp_get_session_snapshot_by_conversation_core`）。这个修复一并解决。

教训写进了 `LESSONS.zh-CN.md` **L15**：「只生效一次」这个形状先怀疑索引/绑定丢失，
别去查业务分支；分清「方向」和「次序」；静默成功比报错难查十倍。

- 测试段落（两个运行时的全套门 + 共享热 target 目录 + 退出码陷阱的英文原文）
- 约束段落（不扩大范围 / 不写无故障路径的防御代码 / 十语齐全 / 别碰哪些目录）
- 报告要求（**"发现了但故意没动"的清单最有价值**，它是下一批活的输入）
- 验收纪律（自己重跑门 / 只看它那个提交 / 机械性声明要机器对拍 / 心跳判活死 /
  UI 改动不能只看单测）

**别凭记忆重写这些，去抄 §7.1。**

## 8. 收尾清理（合完之后）

用户的要求：**合过的才删，分支保留以防回溯。**

```bash
git worktree list
git worktree remove "<路径>"
git worktree prune
# 分支留着，不要 git branch -d
```
