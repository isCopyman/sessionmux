# Codeg Session Workbench 产品需求与使用场景

> 这份文档给产品使用者和需求提出者阅读。  
> 它只描述最终使用效果、默认交互、先后顺序和验收标准。数据库、字段、协议和兼容细节由其他
> RFC 记录。

## 1. 一句话产品

> 在一个 GUI 里继续 Claude Code、Codex、Gemini、OpenCode 等原生 Session，像文件一样整理，
> 像 IDE 一样分屏，并把一整套工作现场保存下来随时切换。

它首先是一个 **Session 管理器和工作台**，不是 Issue 系统、Agent 团队平台，也不是新的
Harness。多 Agent 协作可以以后叠加，但不应成为使用普通 Session 的前置步骤。

### 当前开发进度（2026-08-16）

已经落地的基础包括：Codex Desktop 人工会话名优先显示；数据库中的命名 Workbench；侧栏创建、
重命名、删除和切换；不同 Workbench 的 Session 标签、分屏树、活动项及未发送草稿分别恢复；
旧用户的原布局自动进入 `Main` Workbench；桌面与 Web 共用同一套接口；`Ctrl/Cmd+K` 默认搜索
全部 Folder，并能把标题/属性命中与可选 ctx 正文命中分区展示；侧栏已有全局“会话中心”入口，
可以按 Folder、分支、Workbench、Harness、状态和正文筛选，批量更新、删除，或把多条 Session
一次加入当前 Workbench。会话中心单击只在右侧读取最近历史，不启动 Harness、不改变布局；双击、
Enter 或明确按钮才把 Session 加入或聚焦当前 Workbench。每条结果还能显示它已在哪些 Workbench
打开，并可从预览直接切到其中一个位置；窄窗口中列表和预览自动切换，不再把两栏硬挤在一起。
搜索仍只有一个输入框，旁边可明确限制为“标题与元数据”或“会话正文”，默认同时搜索两者。
Session 现有独立归档状态：可在会话中心批量归档、切到归档视图并恢复；归档不会改变进度状态、
关闭 Workbench 标签、停止运行或删除原生历史。
运行中 Session 已有后端权威、SQLite 持久化的后续消息队列，支持拖动排序、编辑、删除、暂停、
重试、忙碌竞态回队、原子认领和空闲后逐条发送；刷新、关闭最后一个 View、重启和多个客户端读取
的是同一份 revision。当前仍缺的是“已被 Harness 接受以后，这个 Turn 最终完成、失败还是中断”
的统一只读投影，不能只看队列为空就声称任务已完成。
Collection 的第一批可用闭环也已落地：按分类视图采用 `Path → Collection → Session`，每个
canonical Path 下显示可嵌套分类树和自己的“未分类”，可创建、重命名、
移动或删除分类；会话中心可按某个分类及全部子分类筛选，也可把多条 Session 批量移入同一个
分类。每个 Session 最多一个主要分类；删除分类只让其中 Session 回到“未分类”，子分类上移
一级，不修改 cwd、Folder、worktree、Workbench 标签或运行状态。左栏现在把全部命名 Workbench
显示成可展开树，当前工作台默认展开并高亮，每个工作台下面直接列出其中 Session；Collection
展开后也可直接显示成员 Session，worktree Session 仍按真实 cwd 运行，但整理时归入它的 canonical
Path。原来的 Folder 会话树**没有删除**，并重新作为默认 Session 树；
它继续承担按唯一 cwd、仓库、分支和 worktree 浏览及创建 Session 的入口。Collection 是可从视图
菜单切入的语义整理方式，也可在会话中心筛选和批量维护；侧栏不再为两种组织方式永久占用一行
平级标签。
Session 标签（包括尚未发送的新会话草稿）可拖到当前或其他 Pane：中央约 40% × 40% 的区域表示
加入该标签组，中央以外按最近方向显示半屏吸附预览，松手即建立左、右、上或下分屏。投放预览
带边界迟滞。拖起后原 Tab 留在原位并降权显示，鼠标下只移动浮动副本；回到原 Tab 条松手才一次
提交排序，进入 Pane 内容区后只计算布局，不再让排序和吸附互相抢写。左侧 Workbench Session 与
顶部 Tab 使用同一焦点状态做轻量标记。组内换序和跨 Pane 移动不会重启 Harness 或清空已加载的
消息。ctx 不可用时自动退化为元数据搜索。

窗口顶部现已显示 Workbench 标签，Session 标签位于其下；点击工作台会恢复整套 Session 和分屏，
恢复目标显示加载状态，`+` 可立即创建一套工作台。工作台可置顶，也可用拖拽、右键菜单或键盘
调整同一区段内的顺序，并可复制为新的独立工作台；复制会保留已打开 Session 的引用和分屏布局，但不会复制设备本地的
未发送草稿。仍在开发的关键体验包括：Workbench 归档和最近关闭；Collection 拖放、手工排序
和更多快捷视图；Workbench 在语义树中的归档；路径视图的可选 Harness 分组；Session 的更多
显式打开位置；可选系统多窗口；文件/网页资源跟随；Session 间通信与可选群聊。现有
`completed` 仍然只是工作进度，归档已经作为独立状态实现。
因此下面描述的是目标产品，不能把尚未完成的部分当作当前版本说明。

## 2. 用户只需要理解三个东西

### 2.1 Session：真正可继续的对话

Session 是最核心的资产。它保留原 Harness 的身份、历史和 Resume 能力。Codeg 负责统一发现、
显示、打开和同步，不复制一份假历史作为第二事实源。

一个 Session 还可以有 Codeg 显示名、收藏和归档状态，但修改显示方式不应破坏原生会话。
创建或继续 Session 时，模型、思考强度、权限和 cwd 都按该 Harness 的真实能力保存；Workbench
不会强迫其中所有 Session 使用同一种配置，也不显示无法生效的统一选项。第一阶段每个 Session
只有一个主 Folder/cwd，不提供多根 Workspace 或额外目录列表；需要在不同路径工作的 Session
分别创建，再按需放入同一 Workbench。

### 2.2 Collection：长期放在哪里

Collection 类似某个项目路径下的文件夹，回答“以后去哪里找到这段对话或工作现场”。它可以在
自己的 canonical Path 下任意嵌套：

```text
Path：项目 A
├── 资料调查
├── 方案设计
└── 未分类
```

Theme、Chapter、Subproject 都不必成为新对象；用户给某层 Collection 起相应名字即可。Path 是
真实 cwd/worktree 的执行边界，不需要用户把它再手工复制成一层 Collection；第一版一个 Collection
只属于一个 canonical Path，不能把多个 Path 的 Session 混装进同一 Collection。跨 Path 的临时
组合由 Workbench 完成。
一个 Session 第一版只有一个主要位置，也可以暂时处于“未分类”。一个 Workbench 同样可以选择
一个主要 Collection 作为它在树中的位置；这只负责找回工作台，不限制其中 Session 来自哪些
Collection 或路径。最近、收藏和搜索结果只是引用，不会制造多份归属。

Collection 不改变 Session 的 cwd、Folder、worktree、模型或权限。移动 Collection 只是整理，
不是迁移代码或重启 Agent。

左栏保留一个很轻的“当前打开 / 最近 Workbench”快捷区。普通浏览默认沿用 Folder/cwd 树，保证
从路径创建、导入、分支和 worktree 等高频入口不消失；需要按主题整理时，从视图菜单切到
以 Path 为根的 Collection 树，或进入会话中心批量维护：

```text
[按分类]  [按运行位置]
```

“按分类”显示 `Path → Collection → Session`，每个 Path 内可嵌套 Collection；“按运行位置”沿用
原来的 Folder/cwd、仓库和 worktree 树，并作为默认视图。路径下 Session 很多时，可以再选择仅用于显示的
`路径 → Harness → Session` 分组。两种视图引用同一批 Session，不复制历史，也不改变归属；
把 Session 拖进 Collection 只改变语义归档，绝不改变它的 cwd。

### 2.3 Workbench：现在怎样摆着工作

Workbench 是一套可命名、可恢复的工作现场，保存：

- 打开的 Session；
- Pane、内容标签、分屏方向和比例；
- 当前活动内容、必要的草稿和界面状态；
- 后续可加入的固定文件、Diff、图片和网页。

Collection 回答“长期归档在哪里”，Workbench 回答“眼前把什么摆在一起”。同一个 Workbench
可以混放不同 Collection、不同目录和不同 Harness 的 Session；同一个 Session 也可以在不同
Workbench 中被引用，底层仍是同一段对话。Workbench 自己可以像文件一样放入某个 Collection，
从而形成 `Collection → 子主题 → Workbench` 的层级；不使用 `Workbench → 子 Workbench` 表达
归档关系，避免再维护一套与 Collection 重复的目录树。

### 2.4 其他名词都不应成为负担

- **系统窗口**只是普通 Windows/macOS/Linux 窗口；一个窗口可打开多套 Workbench。
- **cwd / Execution Context**是 Session 的唯一运行位置，不做成用户必须先选择的 Workspace
  层级，也不在第一阶段扩展为多路径 Project。
- **搜索范围、筛选和排序**只是找东西的方式，不生成新的产品对象。
- **Room**只在用户显式建立共享讨论时出现；**Team、Issue、Task**都不是日常 Session 管理的
  必建容器。

## 3. 主界面

```text
┌──────────────────┬──────────────────────────────────┬─────────────────┐
│ 当前工作台        │ [方案讨论] [结果审查] [+工作台]   │ Context         │
│ ├ 方案讨论（当前） │                                  │                 │
│ │ ├ Claude       │ ┌────────────┬─────────────────┐ │ 当前 Session    │
│ │ └ Codex        │ │ Claude     │ Codex           │ │ 属性 / 文件     │
│ [按分类][按位置]   │ │ Session A  │ Session B       │ │ 网页 / Diff     │
│ Path：项目 A      │ ├────────────┴─────────────────┤ │                 │
│ ├ 资料调查        │ │ Gemini Session C              │ │                 │
│ └ 未分类          │ └──────────────────────────────┘ │                 │
└──────────────────┴──────────────────────────────────┴─────────────────┘
```

界面使用熟悉的文件树、列表、标签和分屏。聊天正文不做成无限画布；画布或卡片视图以后最多作为
管理大量 Session 的可选总览。

## 4. 真实行为与日常用户路径

这套设计必须同时容纳几种不同但都很普通的行为：

- 一个 Session 通常围绕一个主题，但长会话可能逐渐漂移到新话题；
- 几个 Session 可以属于同一主题，却完全不需要互相通信；
- 多个 Harness 可能对同一问题分工，也可能只是让用户逐个比较；
- Session 之间有时只发生一次咨询或转发，不值得因此创建长期团队；
- 少数长期协作需要一条所有成员都能查看、但只在被点名时才启动 Agent 的共享时间线；
- 用户主要靠最近、名称、目录和布局找回工作，自动编排只是少数需求。

因此，“放在同一 Collection”“摆在同一 Workbench”和“发生消息投递”必须彼此独立。系统不能
根据共处关系自动建群、广播或改变上下文。

### 4.1 找回并继续一段旧会话

1. 在侧栏浏览最近、收藏或 Collection；
2. 也可按 `Ctrl/Cmd+K` 输入标题、Harness、路径，或者记得的对话正文；
3. 标题和属性命中立即出现，跨 Harness 正文命中随后补充，并显示匹配片段；
4. 点击 Session，它加入当前 Workbench 或聚焦已打开位置；
5. Codeg 使用原生 Session ID Resume，而不是创建新会话并重读全部历史。

用户不需要预先判断自己是在“按名称查找”还是“按内容查找”。同一个搜索框同时检索 Session
属性和已建立索引的用户消息、Agent 回复等会话正文；同一 Session 的多条命中合并展示，避免结果
列表被长对话淹没。完整的“会话管理”复用同一查询，只额外提供复杂筛选、更多命中预览和批量
整理，不是使用正文搜索的前置入口。

### 4.2 整理长期 Session

1. 新导入但尚未整理的 Session 进入“未分类”；
2. 拖入一个 Collection 完成归档；
3. 需要时重命名、收藏或归档；
4. 移动 Collection 不关闭已打开 Session，也不中断后台运行。

#### 重命名与同名会话

- 用户在 Codeg 中重命名后，Collection、Workbench、消息投递和多窗口视图保持原对象，不因标题
  改变而重新导入或断开关系；
- Harness 支持原生改名时可以提供“同时同步到 Harness”，不支持时只保存 Codeg 本地名；外部标题
  后续刷新不能覆盖用户明确设置的本地名；
- 名字允许重复，侧栏以 Harness、模型、路径/Collection、活动时间和必要的短 ID 区分；
- 搜索可以命中曾用名，`@` 或发送目标若仍有多个候选必须要求选择，不默认发给第一个；
- 历史消息可以显示当前名称，但详情中保留发送时名称和稳定 Session 身份。

### 4.3 围绕一个主题同时使用多个 Harness

1. 从任意 Collection 找到相关 Claude、Codex、Gemini 等 Session；
2. 把它们打开到同一个 Workbench；
3. 拖到 Pane 边缘形成左右或上下分屏；
4. 用户逐个阅读、发送和比较结果。

这已经覆盖最常见的“多 Agent”使用方式，不要求先建团队、分配角色或启动自动群聊。

### 4.4 在指定项目路径中创建 Session

1. 用户可以从“按运行位置”树的某个 Folder、仓库或 worktree 节点直接新建 Session；
2. 也可以在任意新会话草稿顶部选择本地/远程主机、Folder、分支或 worktree；
3. 全局“新建会话”默认沿用当前活动 Session 的执行位置；没有活动 Session 时使用该 Workbench
   最近一次创建会话所用的位置，仍允许发送前修改；
4. “打开文件夹”会把新路径加入可复用的位置列表并持久保存，以后不必重新输入；
5. 从某个 Path 或其 Collection 新建时，默认使用该 canonical Path；发送前仍可明确改选另一个
   Path，改选后不能继续自动归入原 Collection；
6. 导入原生 Session 时按它真实记录的 cwd 放入运行位置视图，并可在同一步选择 Collection。

因此可以同时做到“按项目路径开始工作”和“按人类主题整理历史”。把 Session 拖入 Collection
不会移动目录；切换新会话的 Folder 只允许发生在第一条消息发送前，已有 Session 不能靠改下拉框
伪装成另一个 cwd。

### 4.5 保存和切换工作现场

1. 给当前 Workbench 命名；
2. 打开另一套 Workbench 处理其他主题；
3. 原 Workbench 中的运行任务继续，布局和草稿保留；
4. 切回来或重启 Codeg 后，原 Session、标签和分屏恢复。

### 4.6 在很多会话中集中整理

1. 打开“会话管理”；
2. 按 Collection、Workbench、Harness、状态、cwd 和时间筛选；
3. 单击只预览，确认后再打开；
4. 多选 Session 批量移动、收藏、归档或加入当前 Workbench；
5. 关闭管理页后回到原工作现场，不改变布局和运行状态。

### 4.7 一段长会话换了话题

系统不自动 Fork，也不为每次话题变化制造新 Session：

- 短暂岔题继续留在原 Session；
- 确实成为长期独立方向时，用户显式新建或 Fork，再命名和归档；
- 若已有相关历史 Session，未来可以建议恢复它，但必须由用户确认；
- 原 Session 跨越多个主题时，可以放在较宽泛的 Collection；第一阶段不做逐消息分类。

这个规则避免“分支爆炸”，也保留了在真正需要时分离上下文的能力。

### 4.8 建立一个共享讨论室

当几个 Session 不只是并排比较，而是确实要围绕同一主题持续互相回应时：

1. 多选现有 Session，创建一个群聊面板；
2. 给群聊命名，并选择放入某个 Collection；若成员原本都在同一 Collection，界面可默认建议它；
3. 群聊作为普通内容标签加入当前 Workbench，右侧显示成员；
4. 用户可以选择“仅发到群聊”、`@` 一个或几个成员，或显式 `@all`；
5. 群里的消息对所有成员可查，但只有被点名的 Session 被启动；
6. Agent 在群里 `@` 另一个成员时，消息仍公开显示，只有新目标继续运行；
7. 点击成员头像进入它原来的 Session 私聊，私聊内容不会自动回流群聊。

每个成员保留自己的 Session 名称，还可以像通讯工具的群昵称一样，在当前群聊中设置更短的昵称
或职责，例如同一个 Session 在“方案讨论”中叫“文献调研”，在“最终审查”中叫“逻辑顾问”。用户
可以按 Session 名称、群内昵称或职责选择 `@` 目标；界面在发送前把它解析成具体 Session，并在
重名时要求选择。昵称和职责只帮助人理解与点名，不创建另一份 Agent 身份。

同一个 Workbench 中打开的 Session 不会自动变成群成员；没有打开在前台的 Session 也可以是
群成员并在后台排队或运行。群聊解决“共享时间线”，Workbench 仍只解决“眼前怎样摆放”。

群聊第一版和 Session 一样只有零或一个主要 Collection，也可以暂时处于“未分类”。它在
Collection 树中使用群组图标，与该主题的普通 Session 并列显示。移动或删除群聊的 Collection
归档只改变以后去哪里找到它，不移动成员 Session、不修改成员各自的 Collection，也不改变 cwd。

消息只有两种容易理解的范围：发在群聊里就是所有群成员可查的公开消息；从成员头像进入原
Session 后发送就是私信，不出现在群聊中。产品心智接近“群聊 + 联系人私聊”，不要求用户选择
复杂的 Channel 类型。群聊内部保留回复关系：点击某条消息可以在侧栏展开围绕它的回复串，适合
收拢多个 Agent 对同一问题的回应。回复串只是同一群聊时间线的局部视图，不拥有独立成员，不是
新的 Session、Room 或 Collection；只有支线长期独立后，用户才显式把它提升为新 Room。

### 4.9 用几个实际场景判断是否真的需要群聊和 Thread

#### 场景一：独立征求多个模型的意见

用户想让 Claude、Codex 和 Gemini 分别评价一个方案，又不希望后回答者受到前面答案影响。用户
多选三个 Session，选择“分别发送”。系统把同一条消息独立送入三个原 Session，每个 Session
继续使用自己的历史，彼此看不到其他接收者及其回复。用户在 Workbench 中分屏比较即可，不创建
Room，也不创建 Thread。

这和群聊中的 `@all` 不同：分别发送得到三段互相隔离的私聊；`@all` 产生一条所有群成员可查的
公共消息。多目标私信仍是多个独立投递，不是“多人私聊”。

#### 场景二：从群聊转去单独追问

某个 Agent 在 Room 中指出一个问题，用户只想继续追问它。用户点击成员头像进入原 Session，
引用那条群消息后发送。追问和回复留在该 Session，不回流 Room；若结论后来值得共享，用户再
执行“分享到群聊”，生成一条带来源引用的新公共消息。

#### 场景三：让几个 Agent 共同形成结论

用户在 Room 中有三种容易区分的写法：

- `@GPT 请检查文献依据`：消息进入公共时间线，只有 GPT 被启动；其他成员以后可以查到，但不会
  因此执行一轮；
- `@GPT @Claude 请分别分析并互相检查`：GPT 和 Claude 获得同一条公共消息，各自启动一次；
- `@GPT 请你和 Claude 协作`：只有被真正选中的 `@GPT` 立即启动。“Claude”只是正文中的名字；
  GPT 判断需要协作后，可以在群里公开 `@Claude`，也可以向 Claude 私信。

Agent 从群聊触发后默认回复原 Room，也可以在公开回复中点名下一位成员继续。界面把这种点名显示
为自然的 `@Claude`，底层则使用结构化目标和稳定 Session ID；普通生成文本中的同名字样不会误
触发另一成员。每次只启动明确目标，并受轮数和停止条件约束。

用户也可以直接 `@all` 请多个成员分别判断。它们并行启动时，只能获得消息发出当刻的公共上下文，
不会自动看到其他 Agent 稍后产生的答案。第一轮结束后，用户可以再 `@审查`，让它结合前面几条
公开回复总结分歧。

即使某个成员因为忙碌而晚些才开始，同一条多目标消息产生的所有成员也使用相同的上下文快照，
以上述触发消息为上界，不因其他成员已经先回复而静默改变首轮输入。主时间线显示“已回复 n/m”，
帮助用户判断何时进入第二轮。

#### 场景四：同一 Room 同时讨论多个问题

如果一个 Room 中同时出现“方案是否成立”和“结果怎样表达”两个问题，多个 Agent 的回复平铺在
主时间线中会难以辨认。此时点击某条根消息，在右侧展开围绕它的回复串。Thread 沿用 Room 成员
和公开可见性，只整理回复关系；其中仍然只有被点名的成员运行。主时间线可以只显示根消息、回复
数量和最新状态。

#### 场景五：Agent 私下分别咨询多个 Session

一个 Session 也可以把同一问题私下发送给多个目标。每个目标独立处理，结果留在各自 Session，
同时以定向回复记录显示在发送者的协作区域。回复到达只更新“3 个目标、2 个已回复、1 个仍在
排队”等状态，不自动启动发送者的新 turn。发送者以后被用户继续或被明确点名时可以看到这些
回复；只有自动汇总成为稳定高频行为后，才增加超时、回收和重新启动发送者的流程。

#### 场景六：Thread 已经成为长期支线

某条回复串持续数天并形成独立目标时，用户可以显式“提升为新 Room”，选择成员，并带入根消息、
人工确认的摘要和返回原 Thread 的链接。系统不自动提升，也不把每次岔题都变成新 Room，避免再次
出现分支爆炸。原 Thread 标记为“已提升到 Room：名称”并默认折叠；继续回复时先提示跳转，避免
原 Thread 和新 Room 同时成为两条主线。

#### 场景七：把文件交给群成员处理

用户把一个文件或若干文档附加到 Room 消息并 `@审查`。附件属于这条公共事件的快照，Room 成员
可以看到文件名、来源和当时版本；被启动的成员在本地可访问时直接读取快照，远程不可访问时明确
显示降级或由 Codeg 随投递传输附件，不能只给出一个对目标机器无效的宿主机路径。Agent 后续把
结论分享到 Room 时保留原附件和消息来源引用。

#### 场景八：同一个 Session 同时参加多个 Room

同一个持久 Session 被两个 Room 点名时，Codeg 对该 Session 全局排队，不并发创建两份假上下文。
它仍可能记住自己在另一个 Room 中实际处理过的内容，因此不能提供真正盲评或保密隔离。用户需要
严格隔离时，应为不同 Room 使用不同 Session 或显式 Fork，而不是依赖 Room 名称隔离记忆。

### 4.10 联系其他 Backend 或 Codeg 管理边界之外的 Agent

当前直接使用 AgentBus 时，一次普通协作也要求用户或 Agent 记住 project、role 和真实 Session
绑定，完成注册、检查 owed/inbox、发信，并在每次被唤醒后重新进入 `recv --wait`。这种方式适合
跨 App、Docker 和远程主机的可靠邮箱，但不适合作为 Codeg 内部日常协作界面。

**远程不等于外部。** Codeg 桌面端已经可以把独立窗口连接到远端 `codeg-server`，所有请求和
WebSocket 事件由该远端 Backend 处理；远端机器上的文件、Harness 和 Session 仍然是 Codeg 受管
对象。对这种 Session，Codeg 应直接使用远端 Backend 的 API/运行时投递，不经过 AgentBus，用户
也不需要注册任何 Bus 身份。

Codeg 内部的核心原则是：**Session Registry 本身就是通讯录，持久 Session 本身就是地址。** 用户
可以在输入框键入 `@会话名`，从候选中选择目标；界面显示会话名、Harness、Collection/cwd 等
辨识信息，实际投递保存稳定的 Session Address：同一 Backend 内是 Conversation ID，跨 Backend
时是 `backend_ref + conversation_id`。会话名只是人类可读标签，重名时必须让用户
消歧，重命名后也不能改变投递身份。第一次发送只产生一条 direct collaboration event 和“最近
联系”记录，不需要先注册角色、创建 Team、加入 project 或让接收方驻留在等待命令中。

这里仍要区分“可寻址”和“可执行”：只读导入的 Session 可以被找到和引用，却未必能够 Resume；
繁忙 Session 会排队；外部未托管 Session 可能只能收到 mailbox。目标选择之后，Codeg 再依据
能力显示“已注入运行时、正在恢复、已入邮箱、只读/不可投递”，而不是在发送前让用户学习底层
协议。

还要区分“消息到了”和“启动 Agent 处理”。一条消息可以先出现在目标 Session 的往来记录和
未读状态中，而不立即花费一次模型调用；用户或发送方也可以明确要求目标空闲后自动处理。回复
是否需要再回传，与是否启动模型是两个独立选择：自动回复默认只显示给原发送者，不因为收到
回复就再次唤醒它。

| 用户动作 | 默认结果 |
|---|---|
| “告诉 Fable 这个结论，不用处理” | 保存并显示，不启动 Fable |
| “请 Fable 有空后审查并回复” | 空闲时启动一次，结果写回来源 |
| “先把问题留给 Fable，下次继续时再看” | 保存为待处理，Fable 下次自然启动时一起看到 |
| Fable 返回审查结论 | 来源 Session 显示回复，不自动启动来源 Agent |

用户也不需要教每个 Harness 记住一整套通信命令。Codeg 始终提供最基本的目标选择、来源标记和
安全边界；当用户要求某个 Session 联系、转交、征求意见或等待其他 Session 时，再按需加载一份
轻量的协作说明（Skill）。这份说明可以包含单次咨询、多目标发送、回复和失败处理的具体例子，
但不会代替真实的消息投递，也不会要求用户先注册 project、role 或 Team。即使 Skill 没有加载，
其他 Agent 发来的消息仍不能被误认为用户授权，标题重名也不能绕过目标消歧。

这几种状态必须在发送前用普通语言表达，不能让用户理解 `wait`、steering 或协议字段。完整的
消息、显示和模型调用边界见
[Session 间通信与调用策略 RFC](./SESSION-COMMUNICATION-RFC.zh-CN.md)。

目标体验是：

1. 对当前 Codeg Backend 管理的本地或远端 Session，用户通过结构化 `@` 或目标选择器选择人类
   可读的 Session；Backend 使用稳定 Conversation ID 直接 Resume 或向已有 Runtime 注入消息；
2. 对桌面端已连接的另一个 `codeg-server`，用户仍选择普通 Session；系统使用带 Backend 身份的
   Session Address，经认证的 Codeg API 投递，不因为网络距离引入 Bus project/role 或模型 wait；
3. 对多个 Codeg Backend 之间需要离线可靠、跨 Room 或 Agent 自主交接的情况，后续可使用直接
   Codeg-to-Codeg 协议，或把 AgentBus 作为隐藏的持久传输 Adapter。一次性地址绑定由系统维护，
   不暴露为日常注册流程；
4. 对未被任何 Codeg Backend 管理的 Codex/Claude Desktop 或其他外部 Session，用户只在第一次建立并确认
   外部绑定；以后仍从 Session、联系人或 Room 成员发送，Codeg 后台桥接器负责 AgentBus inbox、
   owed、reply-to 和重试；
5. Agent 完成当前 turn 后正常结束。后台桥接器等待后续消息，并在能力允许时恢复 Session；不能
   主动唤醒的外部目标则明确显示“已入邮箱，等待外部领取”，不伪装成已经收到；
6. AgentBus project、role、session id、takeover 和 daemon 状态只出现在高级“外部通信”页面，
   不成为创建 Collection、Workbench、Room 或发送普通消息的前置步骤。

例如用户要求当前 Session 向 Fable 征求意见时，日常界面只显示“发送给 Fable”和投递状态。当前
Agent 不应为了等待回复而永久占用一个 turn；Fable 的回复到达后，Codeg 可以把它显示为通知、
加入原回复串，或按用户选择恢复当前 Session，默认不创建新的模型 turn。只有用户明确要求同步
等待时，才把等待作为这一次协作动作的状态，而不是要求每个 Agent 自己维护长轮询。

### 4.11 通过 SSH 接入一台远端工作机

用户的项目、Harness 配置和历史 Session 已经位于实验服务器或另一台电脑上，但不希望手工安装、
启动并暴露一个 `codeg-server`：

1. 在 Codeg 中选择“添加 SSH 主机”，复用系统已有的 SSH config、密钥或 Agent；
2. Codeg 检测远端系统，自动安装或更新兼容的轻量服务，只监听远端回环地址；
3. Codeg 建立 SSH 隧道，远端的 Folder、Harness 和 Session 像普通受管对象一样进入现有侧栏、
   Collection 和 Workbench，不再出现一套独立的“远程工作区”界面；
4. 用户关闭窗口或短暂断网后可以重新连接；正在运行的任务若可恢复，应重新附着，不能悄悄创建
   一份新 Session；
5. 项目文件、Git、Harness 配置和原生会话历史留在远端。本机 SSH 私钥不得上传；默认使用远端
   Harness 已有的登录和模型配置，不自动把本机 API Key 复制过去；
6. 用户仍可显式查看连接状态、远端服务版本、运行主机和停止服务，但不必理解端口、daemon、
   WebSocket 或部署命令。

SSH 只解决“怎样安全到达并启动一个 Codeg Backend”。Session 仍由原生身份唯一标识，Workbench
仍只保存显示现场，Collection 仍只负责分类。连接远端不能复制 Session，也不能让同一段会话因为
本地和远端入口不同而出现两个事实源。

### 4.12 让一个 Session 临时找其他 Harness 帮忙，并继续追问

当当前 Session 需要一次独立调查、实现或审查时，用户或 Agent 可以选择另一个 Harness，并说明
任务。Codeg 创建一个真实的新 Session，注入任务和用户明确选择的必要上下文，把它作为子会话
嵌套在来源 Session 下，完成后把状态和必要结果回到来源处。旧 `delegate_to_agent` 三工具直接
移除，不保留兼容入口；目标体验由未来普通 `create_session + send_message` 提供，不再创造一类
脱离 Session 管理的 Agent/task 对象。开发期在 `create_session` 落地前，Agent 暂时不能主动新建
Session，但现有 Session 间发送与用户在 UI 新建会话不受影响。

父 Session 中的悬浮卡只负责快速查看状态、阻塞原因和结果摘要。点击主动作后，Codeg 把**同一个
子 Session**作为普通内容标签加入当前 Workbench；用户在那里继续输入、Resume、Fork、搜索历史，
或和其他 Session 并排比较。它不是另开一个只能阅读、无法继续的聊天副本。可选的只读 Peek 可以
保留，但不承载第二份 transcript、草稿或 runtime。

如果第一次结果不好，用户可以：

- 在 Workbench 打开同一个子 Session 并继续追问，让它使用刚才的完整上下文改进；
- 从这个子 Session Fork 一个替代方向；
- 明确再创建一个冷 Session 做独立复核；
- 把有长期价值的子 Session 固定到 Collection 或 Workbench，继续作为普通 Session 使用。

临时子 Session 默认嵌套，避免一次并行调研把侧栏变成大量顶层会话；固定为长期 Session 后仍保留
“来源于哪次委派”的关系。系统不会自动删除子 Session 或把完整子对话复制进父 Session，父 Session
只收到任务状态、必要结果和可跳转的来源引用。

当用户进一步要求“把这几个 Session 左右排开”“打开它刚才提到的文件”“切到审查工作台”时，
Agent 可以调用 Codeg 的结构化工作台控制能力。此类操作默认不抢焦点、不关闭现有内容；只有用户
明确要求展示或切换时才改变当前 Workbench。布局、Session 生命周期和消息发送共用 Codeg 后端，
但在产品上仍是三个可独立使用的动作。

### 4.13 把紧急修正送进正在运行的 Session

一个 Session 正在执行较长的调研、工具调用或代码任务时，用户或另一个 Session 发现了会使后续
工作走错方向的新信息。普通消息仍然排队，不打扰当前任务；标为紧急只会提高可见性和队列顺序，
不会自动停止对方。

队列是这个 Session 的持久待发送列表，不是某个聊天窗口的临时装饰。用户可以在 Agent 运行时
连续写下多条后续消息，并对尚未进入模型上下文的条目执行：

- 拖动调整发送顺序；
- 取回输入框完整编辑，保留图片、粘贴文本、文件和当时选择的模式；
- 删除或撤销删除；
- 在 Harness 真正支持时，把某条消息“尽量插入本轮”；
- 把一条独立问题另开为侧边 Session，而不污染当前长任务。

切换 Workbench、关闭最后一个 View、刷新、重启或从另一个系统窗口打开同一 Session 后，仍应看到
同一队列和顺序。两个窗口不能各自发送一次：后台只允许一个执行者原子认领队首，成功后删除；
失败则保留原消息并显示原因。用户主动停止当前响应后，剩余队列默认暂停，避免系统在用户检查
现场前立刻启动下一轮；用户可以继续、逐条重试、编辑或删除。所谓“关闭排队”只改变以后发送
follow-up 时默认选择“排队”还是“尽量插入”，不能静默清空已经排好的消息。

用户在投递状态旁可以选择：

- **尽量插入本轮。** Codeg 只在当前 Harness 明确支持 steering 时，将消息放到它声明的安全断点；
  若能力不足或本轮恰好结束，消息回到普通队列，界面说明实际发生了什么；
- **停止当前任务并发送。** Codeg 先保存消息，再停止目标当前 turn，确认停止后立即把同一消息
  作为下一轮输入。已有的部分回复、文件修改和工具副作用不会被伪装成撤销，用户可以查看并决定
  是否恢复或重试；
- **继续等待。** 保持消息在队列中，也可以撤回尚未进入 Agent 上下文的投递。

如果消息等待超过用户设定的期限，Codeg 提醒用户是否升级投递，但不自行打断。Agent 可以请求
“尽量插入”，不能仅凭一条消息很紧急就停止另一个 Session；Agent-to-Agent 的强制打断只有在用户
针对该 Session、发送者或协作规则做过显式预授权时才可用。Codeg 受管 Session 优先使用结构化
steer/cancel/prompt；未托管外部 Session 只能在真实支持 hook、停止或恢复时提供相应按钮，否则
显示“已入邮箱，等待领取”。

### 4.14 在大量 Session 往来中找回“谁还没处理”

用户让“文献调研 GPT”把资料发给“正文写作 Claude”，又让“逻辑审查”分别向两者提出问题。几天
以后，用户不应靠记忆猜消息去了哪里，也不需要把 Codeg 当成一套复杂邮箱来管理。

打开某个 Session 的“往来”面板时，只看四类：待处理、收到、发出、全部。跨所有 Session 的消息
中心则只看未读、待我处理、等待对方、失败/逾期和全部往来。用户可以进一步按方向、Session、
Collection、Harness、是否已交给 Agent、是否等待回复过滤，并按最新、最旧未处理、到期或最近
活动排序。搜索同时命中正文、当前标题、发送时标题、参与者、Collection 和附件名。

一条同时发给多个 Session 的消息在发件侧仍是一条记录，展开后分别显示每个目标的真实状态：

```text
请分别审查这段论证
├── 文献调研 GPT：已交给 Agent · 等待回复
├── 正文写作 Claude：UI 已看 · 尚未交给 Agent
└── 逻辑审查：投递失败 · 可重试
```

用户可对单条往来执行“回复、加入下一轮、立即处理、仅参考、稍后提醒、无需回复”。“UI 已看”
只表示人类打开过，不表示 Agent 已经摄入；pending 消息不会伪装成原生聊天内容，也不会自动变成
用户 follow-up。只有正文真正进入某次 Turn 后，时间线才在该 Turn 前显示带来源的协作卡片。

因此，日常协作可以保持轻量：Collection 负责把相关 Session 放在一起，Workbench 负责并排阅读，
往来面板负责可靠投递和找回。Room、Team 和共享群聊时间线仍是后续可选层，不是完成一次跨
Session 协作的前置条件。

## 5. 默认交互规则

### 5.1 打开 Session

Codeg 始终至少有一个默认 Workbench。不存在额外的“非 Workbench 会话模式”。

| 当前情况 | 默认结果 |
|---|---|
| Session 已在当前 Workbench | 聚焦已有位置，不重复打开 |
| Session 尚未在当前 Workbench | 加入当前 Pane，成为固定内容标签 |
| 当前 Pane 已有其他内容 | 新增标签，不静默替换已有固定标签 |
| 只有一个从未输入的空白草稿 | 可以复用该空标签 |
| Session 只在其他 Workbench | 默认也加入当前 Workbench，同时可选择切到原工作台 |

侧栏单击和 Quick Open 的 Enter 使用同一规则。完整“会话管理”中的单击只选中并预览，双击或
Enter 才打开。IDE 式“一次性预览标签”可以保留为偏好设置，但不作为默认行为。

“在右侧打开”“在下方打开”“加入但不聚焦”“在新 Workbench 打开”和“在新系统窗口打开”都是
明确的附加动作，不能由普通单击猜测。

### 5.2 关闭、停止、归档和删除必须分开

| 动作 | 发生什么 | 不发生什么 |
|---|---|---|
| 关闭内容标签 | 从当前 Workbench 移除这个显示位置 | 不删除 Session，不自动停止运行 |
| 从 Workbench 移除 | 关闭该 Workbench 中的显示位置 | 不改变 Collection |
| 关闭 Workbench 标签 | 从当前系统窗口卸载，但保留整套工作台 | 不删除布局或 Session，不自动停止运行 |
| 移动 Collection | 改变主要归档位置 | 不改变 cwd，不关闭 Session |
| 归档 Session | 从日常列表隐藏，仍可搜索和恢复 | 不删除原生历史，不自动关闭或停止 |
| 停止当前运行 | 显式取消或终止当前 turn/runtime | 不等于关闭标签或归档 |
| 删除 Workbench | 删除这套布局 | 不删除其中任何 Session |
| 删除 Collection | 成员移到未分类，或由用户选择迁移目标 | 不级联删除 Session |
| 删除 Session | 单独的危险操作，需要确认影响和原生 Harness 能力 | 不能由关闭标签间接触发 |

提供“最近关闭”以恢复误关的内容标签或 Workbench；危险删除不能混入拖拽和普通关闭流程。

### 5.3 浏览、搜索和筛选

侧栏默认显示按运行位置组织的 Session；低频的语义树切换进入视图菜单，不再永久增加一行主标签：

```text
[工作台] [新建] [搜索] [会话中心]       [视图：按运行位置 / 按分类]
```

- “按运行位置”用于唯一 Folder/cwd、仓库、分支和 worktree，是默认且由 Execution Context
  派生的系统视图；“按分类”仍以 canonical Path 为根，再在其下显示主题、子项目和长期归档。
  两者引用同一批 Session，不是两套 Session，也不会相互改写。
- Collection 拖放通过会话中心、Session 菜单或未来的轻量投放目标完成；反向投放绝不用于改变
  cwd，避免把分类操作误解成移动项目文件或重写原生 Session 的执行上下文。
- “按运行位置”默认 `路径 → Session`；同一路径混有大量 Harness 时可切换为
  `路径 → Harness → Session`。Harness 层只是显示分组，不创建目录或复制 Session。
- Collection 在所属 Path 下直接展开；需要跨目录筛选和批量整理时，再进入会话中心并显示可清除的
  `Collection: 名称`范围标签，不额外提供含义模糊的“当前 Collection”按钮。
- 运行中、等待处理、收藏、最近、未分类和归档是快捷视图或筛选标签，不是新层级。
- Harness、状态、cwd 和活动时间放进轻量筛选弹层。
- 搜索默认作用于当前范围，并始终提供“在全部 Session 中搜索”。
- 默认由同一输入框同时搜索标题/元数据和正文；需要精确筛选时，可切换为仅标题/元数据或仅正文，
  不增加第二个搜索框。
- 筛选后的当前 Session 仍留在内容区；界面提示它不在当前结果中，并可一键清除筛选。
- 运行中、等待处理和审批请求的全局数量始终可见，避免因为筛选漏掉任务。
- 排序、分组和筛选只改变显示，不移动 Session，也不自动生成 Saved View。

侧栏、Quick Open 和会话管理共用查询与打开动作，但承担不同密度：侧栏用于日常，Quick Open
用于键盘直达，会话管理用于展开更多正文命中、组合筛选和批量整理。不再额外增加第四套搜索/
过滤面板。

### 5.4 分屏和 Workbench

- Pane 中央约 40% × 40% 是加入目标标签组的安全区；安全区以外按最近方向显示左、右、上、下
  吸附预览并建立分屏，不要求鼠标贴住细窄边缘；
- 吸附区切换带轻微迟滞，拖动预览不写入正式布局，松手时才提交一次；
- 组内换序不移动已挂载的会话正文 DOM；跨 Pane 重挂不清消息缓存、不重启原 Harness；
- 同一个 Session 在同一 Workbench 中默认只显示一次，再次打开会聚焦；
- Workbench 顶部标签用于切换当前窗口已打开的工作台，侧栏用于管理全部已保存工作台；
- Workbench 可以创建、重命名、复制、置顶、排序、关闭和删除，也可以选择一个主要 Collection 作为
  文件树中的归档位置；
- 切换、关闭或删除 Workbench 不自动停止其中的 Session；
- “放大当前 Session”临时隐藏其他 Pane，退出后原样恢复，不新增所谓 Focus Workbench 模式。

第一阶段 Workbench 的成员就是当前打开的内容标签，不再维护“属于工作台但被隐藏”的第二份
成员清单。

### 5.5 同一个 Session 被多处打开

同一个原生 Session 只能导入为一个 Codeg Session。它可以通过不同 Workbench 或系统窗口拥有
多个显示位置，但这些位置必须：

- 共享已发送消息、流式输出、运行状态、工具调用、审批和用量；
- 不因为打开第二个视图而 Resume 或启动第二份 Harness 会话；
- 各自保存滚动位置、选区、焦点和布局；
- 在发送和取消操作上串行化，避免两个窗口制造冲突 turn。

同一设备上的未发送草稿原则上共享，并在多个输入框同时编辑时明确显示编辑权或接管动作。
如果这套同步尚未可靠实现，物理多窗口就不应提前作为已完成能力宣传。

## 6. Session Library 与会话管理

Session Library 提供：

```text
Quick Access
├── 收藏
├── 最近
├── 运行中
├── 等待我处理
└── 最近关闭

Collections
未分类
归档
```

完整的“会话管理”是应用级工具页，不是 Workbench 内容标签。它复用 `Ctrl/Cmd+K` 的统一搜索，
并至少支持：

- 标题、Harness、Collection、Workbench、cwd、状态和时间搜索；
- 正文命中片段预览；
- 批量移动、收藏、归档和加入当前 Workbench；
- 显示 Session 已在哪些 Workbench 打开；
- 找到尚未导入的原生 Session 后显式导入并继续。

Codeg 自身负责元数据搜索；可选调用本地 ctx 做跨 Harness 正文检索。元数据结果先返回，正文
结果异步补充。ctx 未安装、索引过期或查询失败时，基本搜索仍然可用。搜索结果不能成为 Session
身份来源，也不能在预览时启动 Harness 或修改当前布局。

原生 Session 导入按 Harness + 原生 Session ID 去重。若外部历史文件暂时不可读或被移动，Codeg
先标记“来源不可用”并提供重新定位、重扫或忘记索引，不得仅因一次扫描失败就静默删除记录。

## 7. 后置能力，而不是第一阶段结构

### 7.1 物理多窗口

先把单窗口内的多 Workbench、分屏和恢复做好，再支持“在新窗口打开”、多显示器位置记忆以及
同一 Session 多窗口同步。系统窗口不是新的归档层，也不是核心版本的完成条件。

Workbench 已经解决“保存多套现场并快速切换”的主要问题，因此物理多窗口明确降级为 Bonus：
只有同一 Session 的消息、流式输出、运行状态、审批和发送队列能够可靠共享，而且两个窗口切换
活动 Workbench 不会互相影响时，才开放为正式功能。第一版若保留“在新窗口打开”，可以仅作为
查看或单一可写挂载；不提前实现跨窗口拖放、全部窗口恢复和同一 Workbench 双写布局。

### 7.2 文件、网页和 Diff

Codeg 0.25.0 已经提供文件树、文件和 Diff 标签、Monaco 快速编辑、Git Changes/Log、终端，以及
Markdown、HTML、图片和 Office 等预览。这里不再规划另一套完整 IDE；继续补语言服务、调试器、
插件系统、复杂重构或各类文档编译链，会让 Session 工作台逐渐变成一个不完整的 VS Code。

产品边界是：Codeg 内适合定位文件、查看 Agent 修改、快速编辑、预览、Diff，以及把文件或选区
附加给当前 Session；需要长时间编辑、项目级搜索替换、调试或专业插件时，交给用户已有编辑器。

默认规则只需要两句话：

> 从 Session 打开的资源跟随该 Session；点图钉后固定到当前 Workbench。
>
> 文件和运行目录都提供“打开方式”，可以一键交给 VS Code 或用户配置的外部编辑器。

不向普通用户暴露 Session / Workbench / Global 三档作用域。资源页在 Session 管理和布局恢复
可靠以后再扩展。“在外部编辑器打开”至少出现在文件树右键菜单、文件标签/标题栏和 Session
运行目录菜单：文件尽量带行列位置，目录打开对应 cwd。首次使用可以选择 VS Code、Cursor、Zed
等已检测到的编辑器，之后记住默认值；“打开方式”仍允许临时改用其他目标或系统文件管理器。

本地桌面模式可以直接启动编辑器；Web、Docker 或远程 Workspace 必须识别路径属于哪台主机，
不能把远端路径交给本机编辑器后假装成功。第一版可以明确禁用并说明原因，后续再增加 VS Code
Remote/SSH、远程 URI 或服务端编辑器启动。外部编辑器修改文件后沿用现有文件监听与冲突提示；
Codeg 内存在未保存内容时，先要求保存、放弃或取消，不能静默用磁盘版本覆盖。

[#464](https://github.com/xintaofei/codeg/issues/464) 和
[#465](https://github.com/xintaofei/codeg/issues/465) 已由需求提出者关闭，不再作为当前资源页路线。
未来若出现稳定需求，再以独立能力重新评估，不因已有 Markdown 内嵌渲染而扩大成完整文档 IDE。

### 7.3 Fork、编辑旧消息和文件恢复

这些能力不能都叫 Rewind：

| 动作 | 结果 |
|---|---|
| 从当前状态 Fork | 创建新 Session，原 Session 保留 |
| 从旧消息分叉或编辑后重发 | 从选中位置创建新 Session，原历史不改写 |
| 恢复文件 | 单独预览并确认工作目录变化 |

UI 只显示 Harness 实际支持的能力。第一阶段先保证 Resume 和末端 Fork，历史分叉、文件检查点
和跨 Harness handoff 再按适配器能力实现。

用户从当前 Session 执行 Fork 后，新 Session 作为独立内容项出现在父 Session 附近，并获得可编辑
的建议名称。它默认沿用 cwd、主要 Collection 和普通标签，但不继承群成员身份、角色绑定、排队
消息、等待回复义务、未发送草稿、输入锁或运行中 Turn。父子可以并排打开、分别重命名和分别
寻址；给父 Session 的旧消息不能因为 Fork 自动送达子 Session。重复点击或失败重试使用同一幂等
请求，不得生成多个意外分支。

### 7.4 多 Agent 协作

高频协作首先是“把几个 Session 摆在同一个 Workbench，由用户分别阅读和发送”。下一步可以
增加几个轻量动作：

- 多选 Session，向它们发送同一问题；
- 并列查看和比较回复；
- 把一个 Session 的结论转发给另一个；
- 显示投递、排队和等待回复状态。

在这些基础上增加一个可选的**群聊面板**，用于确实需要共享时间线的协作。产品交互上，每个
持久 Session 都可以作为一个群成员和可寻址 Agent，不必先创建 Team 或角色模板。群聊不是新的
组织层，也不等于 Workbench：它只是一个可加入 Collection 和 Workbench 的内容面板。

群聊遵守三条直观规则：

- 发在群里的内容进入共享时间线，成员以后都能查看；
- 只有 `@` 到的 Session 才启动一次 turn，普通消息可以只作群内记录；
- 点击成员进入原 Session 私聊，私聊及 Session 间私信不会自动公开到群里。

“成员可以查看完整群历史”不表示每一轮都把全部历史塞进模型。被启动的 Session 默认获得当前
消息、回复链、置顶背景和有界的近期上下文，并可按需读取更多历史。Agent 间连续 `@` 必须受
链深、轮数、预算和停止按钮约束。

第一版群聊不增加 Team、隐藏 Master、LLM 自动选人、复杂权限或 Workflow。若以后同一套成员
需要反复用于多个群聊，再考虑保存成员模板。AgentBus 继续承担未托管 App、缺少直接 federation
的跨 Backend 和离线持久 mailbox 的传输能力；群聊时间线仍由 Codeg 保存，AgentBus 不成为
Session 的组织层。

完整行为见[群聊面板与 Session 协作 RFC](./GROUP-CONVERSATION-RFC.zh-CN.md)。

### 7.5 项目记忆、Decision 和自动路由

Session 本身先作为最原始、可追溯的知识资产。自动提炼共识、识别话题变化、建议恢复旧 Session
或维护 `supersedes` 关系都有价值，但必须在 Session 管理可靠以后再做，避免制造过时且无法追溯
的“项目记忆”。

## 8. 实施顺序

### P0：先可信

1. 正确导入、去重和 Resume 原生 Session；
2. 原生标题、人工锁定标题、活动时间和外部增量同步可靠；
3. 侧栏和 Quick Open 采用一致且不覆盖固定标签的打开规则；
4. 关闭、停止、归档和删除行为分离；
5. 外部来源暂时不可用时安全降级，不静默删除索引或历史；
6. 模型、思考强度、权限、Resume/Fork 等选项按 Harness 能力真实呈现。

### P1：完成日常闭环

1. 唯一主要位置的多层 Collection、未分类、收藏和最近；
2. 当前工作台/全部范围、Collection 范围标签和轻量筛选；
3. 可命名、可切换、可恢复的 Workbench；
4. 拖边吸附分屏和布局持久化；
5. 默认位置树保留新建、导入、Folder、分支和 worktree 操作；分类视图采用
   `Path → Collection → Session`，并保留按 Path 新建 Session 的入口；
6. 重启后恢复上次工作现场。

P0 + P1 完成后，Codeg 就应能承担“多 Harness + Session 分组管理 + 分屏 GUI”的核心需求。

### P2：大量会话、资源与可选多窗口

1. 完整会话管理、批量操作和可选 ctx 全文检索；
2. 最近关闭与更完整的恢复；
3. 同一 Session 多视图的实时同步和输入冲突处理底座，为 Web、移动端和可选多窗口共用；
4. 物理多窗口仅作为 Bonus，在同步验收通过后再实现窗口位置记忆；
5. Session 资源跟随与 Workbench 固定；
6. Workbench 放入 Collection、最近/打开工作台快捷区，以及最近 Workbench 快照缓存与预取。

P2 的多视图同步底座有跨客户端价值，但“打开第二个系统窗口”本身可以无限期后置，不影响
Codeg 承担日常多 Harness Session 工作台。

### P3：历史能力与协作

1. 历史消息分叉、文件恢复和跨 Harness handoff；
2. 删除 delegation 三工具，未来用普通 `create_session + send_message` 创建可继续、Fork 或固定的
   持久 Session；
3. 多选发送、转发、比较和状态跟踪；
4. Agent 可调用语义化 Session/Workbench/资源工具，不依赖模拟点击且默认不抢焦点；
5. AgentBus 控制面和外部投递；
6. 能力门控的紧急插话，以及由用户明确触发的“停止当前任务并发送”；
7. 可选群聊面板、显式目标、共享时间线和成员私聊跳转；
8. Agent 间 `@`、上下文游标、链深和预算保护；
9. Team 模板、Decision、项目记忆、自动主持人和 Workflow 最后评估。

## 9. 明确不做什么

- 不强迫每次讨论创建 Issue、Task、Team、Room 或 worktree；
- 不把物理 Folder/cwd 当成人类主题分类；
- 不为一个 Session 增加多个 cwd、Project roots 或额外可写目录；
- 不要求每个 Session 单独拥有一套 Workbench；
- 不重新实现一套阉割版 Harness，也不伪装所有 Harness 能力完全相同；
- 不复制原生会话历史作为第二事实源；
- 不把聊天正文和 Pane 布局做成无限画布；
- 不自动 Fork、自动建群或让多个 Agent 默认抢答并消耗 Token；
- 不把同一 Workbench 中的 Session 自动视为群成员，也不让普通群消息默认唤醒全体；
- 不让关闭标签、删除 Collection 或删除 Workbench 间接删除 Session；
- 不用虚假的“在线”状态掩盖外部 Session 无法主动唤醒的事实。

## 10. 怎样算真正可用

1. 用户可以在一分钟内找到并继续任意重要的长期 Session；
2. Claude、Codex、Gemini 等 Session 可以在同一列表、Collection 和 Workbench 中管理；
3. 新增、重命名和继续过的外部 Session 会可靠刷新，不产生重复身份；
4. 普通点击不会静默覆盖正在使用的固定标签；
5. 用户能清楚区分关闭、停止、归档、删除以及它们的影响；
6. 切换主题时，一次操作即可恢复整套 Session 和分屏，不必重建布局；
7. Collection、搜索和筛选不会改变 cwd、停止运行或制造重复会话；
8. 拖动内容标签到边缘即可完成主要分屏操作；
9. 同一 Session 在多个位置显示时共享一份运行与消息，不启动重复会话；
10. 筛选不会隐藏全局的运行中、待处理或审批提醒；
11. ctx 或某项 Harness 能力不可用时，Codeg 能清楚降级而不是显示无效功能；
12. 不使用任何 Team、Room 或 AgentBus 功能，也能完整完成日常多 Harness 工作。

启用 Session 间通信后，还要做到：普通消息不会打断运行任务；紧急消息能显示真实的排队、插话或
停止状态；不支持 steering 时可靠回队；只有用户或显式预授权策略能停止另一个 Session，且停止
失败不会丢失待发消息。

若用户启用群聊，还必须做到：群消息对成员可查但只启动显式目标；`@all` 发送前显示目标数量；
点击成员可立即进入原 Session 私聊；未打开在前台的成员仍能排队或显示真实不可投递原因；关闭
群聊不停止或删除成员；Agent 间连续交接可以被用户停止并受轮数/预算限制。

达到这些标准后，它才不只是“能打开多个 Agent 的 GUI”，而是可长期使用的 Session 工作环境。
